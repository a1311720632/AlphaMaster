第四步从 paper（已 6 周稳定运行）走向 testnet/live 时，对"服务挂了/数据源挂了"的完整决策集。
本文收拢 2026-08-26 grilling 会话敲定的 14 项决策中难逆转的部分。

**实现落点**（2026-08-26，分支 feat/autopilot-server-deploy）：
`autopilot/ledger.py`（冷账本）、`autopilot/alerts.py`（Alerter 节流）、`autopilot/readiness.py`
（testnet 达标机检）、`web/data_sources/{bybit,binance,fallback}_source.py`（备源链）、
engine 的 peak 回填/执行熔断/心跳/日报、`/api/autopilot/preflight|history`、前端 live 确认
modal + 系统健康面板。OKX demo 端到端首验仍未做——testnet 长跑前的必经关卡。

## 决策

### 1. 断连是两个域事件，不是同一个"断网"（B2）

- **行情断连 = 业务连续性问题**：有替补。备用源链 OKX → Bybit → 币安，平价切换
  （备用源供全窗口 lookback bar，不与主源历史混拼——混拼会让成交量类特征跨源跳变，更脏），
  主源恢复即切回，切换事件进冷账本 + 飞书知会。切换期间的信号漂移算执行摩擦（ADR-0003 口径）。
- **交易断连 = 资金安全问题**：无替补（不能在币安下 OKX 的单，那是另一个持仓宇宙）。
  下单/平仓 bar 内重试 3 次仍失败 → 执行熔断：飞书告警（含当前/目标仓位与最近错误）→ 停机。

### 2. 执行熔断 stay_down，放弃对账自愈（B3）

ADR-0006 的对账自愈（下根 bar delta 自动补齐）本可吃掉瞬时下单失败，但我们选择 3 连败即停机、
watcher 归入 stay_down（与回撤熔断同类），不自动重拉。理由：能穿透"3 次重试"的失败基本是持久的
（凭据吊销/保证金不足/账户限制），重拉无意义且刷屏；**资金安全问题的处置终点是人，不是自动重试**。
停机后仓位静止、可人工处置；动态风险（回撤）由跨重启基线（见下）兜住。
halting 前 flatten 失败的告警必须发出且写明"全平失败、仓位仍在场内"。

### 3. 回撤基线跨重启（B1）

恢复 state 时回填 DrawdownBreaker 的 peak。没有这条，每次进程重启 = 白送一次新的 −10% 额度，
与 watcher 自动重拉组合成静默的风险放大器。换策略文件重启沿用旧 peak = 特性（钱还是那笔钱）；
显式开新回合走"一键清除"。

### 4. 外部 watchdog 管整机死（B5）

进程内 watcher 只能管进程；VPS 整机死时飞书告警也发不出（发送者死了）。引擎每根 bar ping
外部健康检查服务（healthchecks.io 类），超时未 ping 由**活着的第三方**发通知。三层分工：
进程内 watcher 管进程，外部 watchdog 管机器，交易所逐仓强平管世界末日。
不做交易所侧条件单（与 ADR-0001 的"无单笔止盈止损"正面冲突；逐仓 + ≤1x sizing 已是隐性保险）。

### 5. 飞书告警：引擎内直调，日报兼心跳（B4）

autopilot 子进程直接 import `web.feishu_notify.send_text`（纯 HTTP，不依赖 web 进程活着）。
覆盖：熔断类全上、源切换/halt/重启知会类全上、每日权益摘要（摘要停发 = 系统死的次级信号）。
不做逐笔成交推送（噪音）。告警节流：进入失败态发一次、恢复发一次，不逐 bar 重复。

### 6. live 门槛：testnet 长跑 2-4 周（D1/D2）

preflight 过 ≠ 可上 live。testnet 需连续跑 2-4 周，机检清单：连续运行时长、真实订单数（含开+平）、
账实漂移告警数、无 halt、与 paper 同期走势吻合。paper 对照走离线补算（parity 确定性保证
补算 = 实跑），不做双进程并行（单槽架构保留；多槽重构留待多标的需求）。
**上实盘是一个状态，不是仪式**——清单进 live 确认弹窗逐项绿勾。

### 7. 账本分层：hot state + cold ledger（E1）

hot state（cap 1000 的滚动窗口 JSON）解决"现在怎么样"的实时轮询；cold ledger
（append-only JSONL：bar/成交/运营事件）解决"发生过什么"的审计视图。没有分层，
1h bar 下 1000 根 ≈ 42 天，长跑后日历/曲线静默丢头。冷账本按 (symbol, mode) 分文件，
归档规则见 CONTEXT.md "state 三元组与归属"。

## 放弃的方案

- **下单失败靠对账自愈继续跑**（B3 的 (a)）：更贴 ADR-0006 的精神，但执行层坏了继续跑
  = 无人修复也无人停止，与"资金安全终点是人"冲突。
- **行情/交易都无备源，断连统一 halt+无限重拉**：仓位敞口裸奔，重启不是保护只是节奏。
- **SQLite 替代 JSON**：正规但重——改动 parity 关键路径旁的写代码、引入 schema 管理，
  而每天 ~24 行 bar 的量级下 JSONL 已是永远够用的最笨解法。
- **交易所侧条件单兜底**：改仓位、破坏奇偶性，ADR-0001/0005 已排除；逐仓强平已覆盖该尾部。
- **多槽 manager（paper/testnet 并行）**：正确的终态（多标的地基），但为"并行对账"服务时
  离线补算已足够；等真实多标的需求落地再动。
